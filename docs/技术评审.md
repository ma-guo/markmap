- 逐条对照 PRD 第 5 章功能点，评估**实现难度**、**依赖**、**风险**、**工作量**。
- 难度分级：

| 等级 | 含义 | 典型工作量 |
| --- | --- | --- |
| ★ 低 | 有现成 API / 纯逻辑，风险低 | 0.5–2 人日 |

| ★★★ 高 | 涉及数据源、离线、性能或复杂交互 | 5–10 人日 |

## 2. 代码现状关键结论

1. **数据层**：Room `version = 1`，且使用 `fallbackToDestructiveMigration()`（`AppDatabase.kt:45`）。任何加字段都必须改迁移，否则升级丢数据。
2. **百度地图 SDK 7.6.4 能力已确认**（解包 aar 验证）：
   - `BaiduMap.snapshot()` / `snapshotScope()`：支持地图截图 → 分享卡可行。
   - `com.baidu.mapapi.map.offline.MKOfflineMap`：支持离线地图下载/导入 → 离线地图可行。
   - `GradientLineOptions`、`HeatMap`、`ArcOptions`、`MarkerOptions`、`PolylineOptions`：轨迹渐变、热力图、图标均有原生支持。
3. **逆地理编码走自建后端**：`BaiduPlaceService` 调用 `notify.gyzuxing.com/api/baidu/reverse_geocoding/`，**只返回 `address`、`description`**（`BaiduPlaceService.kt:20-28`），**没有结构化的省/市字段**。这是「足迹点亮」的最大技术风险。
4. **定位服务**：`LocationService` 已是前台服务 + `START_STICKY`，`setIsNeedAddress(true)` 但只存了 `addrStr`；`CustomLocationService` 直接使用 GPS/GNSS Provider，**断网仍可用**。
5. **无 FileProvider**：清单未配置，分享/导出/照片需要新增。
6. **无现成分享**：无 `ACTION_SEND`、无截图逻辑，需从零实现。
7. **现有可复用资产**：`Utils.calculateDistance()`（Haversine）、`TrainRouteStitcher`（轨迹拼接）、`LineMapActivity`（折线配色）、`MapActivity`（逆地理编码 + 打点）。

## 4. 关键技术风险与对策

### 4.1 合并轨迹算法（★，已简化为手动合并）

**已确认规则：不设任何自动阈值，合并完全由用户决定。**

- 用户勾选段 → 拖拽排序 → 每段可切正向/反向 → 预览 → 保存方案。
- 相邻段端点不重合时默认虚线连接，可关闭或留空。
- 有时间则在衔接点展示时间差；无时间不展示。
- 不做自动断点/停留阈值判断，避免「算法替用户做决定」。

实现更简单：`TrackMerger` 只需处理「按用户顺序拼接 + 方向反转 + 重合点去重 + 连接线标志」。纯 Kotlin，易单测，预估 **2–3 人日**。

### 4.2 省/市识别（★★★，最大风险）

现状：逆地理编码只回 `address` 文本，无省/市结构化字段。可选方案：

| 方案 | 说明 | 评价 |
| --- | --- | --- |
| A. 修改自建后端 | 让 `/reverse_geocoding` 同时返回 province/city | 最优，但依赖后端可控 |
| B. 记录时取 `BDLocation.province/city` | 新点天然带省/市（已解包验证 `getProvince()/getCity()/getDistrict()/getAdCode()/getCityCode()` 均存在） | 简单，但**历史点无** |
| C. 地址文本解析 | 用省市字典解析 `addrStr`（如「广东省深圳市…」） | 可行，覆盖大部分，需兜底 |
| D. 内置离线行政区划数据 | 省/市 GeoJSON + 点在多边形内判断 | 不依赖网络，包体增大（数 MB），实现成本高 |
| E. 最近城市质心 | 内置城市中心点，按最近距离近似 | 实现简单，边界误差大，仅作最终兜底 |

建议：**B + C 为主，A 为最优补充，D 作为离线兜底可选**。历史数据回填在成就页按需计算并落缓存。

**评审结论（已确认）**：采用 **A + B + C + E** 组合。后端 `notify.gyzuxing.com` 由我方完全掌控，因此 A 方案可落地，并用于历史点回填。

`RegionResolver` 优先级：
1. **A**：后端逆地理返回结构化 `province/city/district`（在线、含历史回填）。
2. **B**：记录时从 `BDLocation.getProvince()/getCity()/getDistrict()/getAdCode()` 直接落库。
3. **C**：用省市字典解析 `address` 文本（离线兜底）。
4. **E**：最近城市质心近似（最终兜底）。
5. 结果写入本地缓存表，避免重复解析；无法识别时标记为「未知」。

### 4.3 航班航线（★★，已确定方案）

**能否从航旅纵横类 App 拿数据？——不建议依赖，基本不可行。**
- 航旅纵横（中航信系）没有面向开发者的公开数据 API；其 App/小程序接口为私有接口。
- 抓包调用私有接口需要登录态、签名/加密参数、设备指纹，常伴随证书绑定（SSL Pinning），接口会随时变更，维护成本极高。
- 抓取/逆向第三方 App 数据可能违反其用户协议，并涉及数据合规风险，不适合随 App 分发。

**可选数据源对比**

| 方案 | 内容 | 成本 | 覆盖/稳定性 |
| --- | --- | --- | --- |
| 内置机场库 + 大圆航线 | 机场坐标（OurAirports 等开源数据）+ 起降点画大圆 | 免费、离线 | 稳定；是「参考轨迹」不是实际航路 |
| OpenSky Network | ADS-B 实际航迹（历史/实时） | 免费/研究向，有限额 | 中国境内地面站覆盖较弱 |
| ADS-B Exchange | 实际航迹 | 历史数据付费 | 覆盖较好 |
| 飞常准 / VariFlight | 航班动态、航线 | 商业 API | 国内覆盖好，需商务合作 |
| FlightAware / Flightradar24 | 实际航迹、航班数据 | 付费 | 全球覆盖好 |
| Amadeus / Cirium | 航班计划与航线 | 商业 | 企业级 |

**建议 M3 落地路径**
1. MVP：内置机场库 + 航班号/起降机场 → **大圆航线参考轨迹**（离线、零成本、可控）。
2. 增强：接入 OpenSky 拉取实际航迹（有则用实线，无则回退大圆虚线）。
3. 商用：如需国内高覆盖实际航路，再评估飞常准/FlightAware 等付费 API。

> 参考轨迹需与用户真实记录区分（实线 vs 虚线），并在 PRD 5.9 FR-9.3 已约定。

### 4.4 离线地图与纯轨迹（★★）

- 离线瓦片：`MKOfflineMap` 可用，但需要城市选择、下载管理、存储清理 UI。
- 「纯轨迹模式」兜底更简单：无网时仍按坐标绘制折线与点，底图空白/灰底即可，不必强依赖离线瓦片。
- 建议 M1 先做「纯轨迹兜底」，离线瓦片下载放到 M3。

### 4.5 分享与文件（★★）

- `snapshot()` 已确认；分享卡用「地图 Bitmap + 信息卡 View 合成」。
- 需新增 `FileProvider`（`xml/file_paths.xml`）与 `ACTION_SEND`。
- 长图（年度报告）注意 Bitmap 内存与 OOM，建议按屏拼接/降低分辨率。

### 4.6 数据迁移（★，但不可省）

- 从 `fallbackToDestructiveMigration` 改为显式 `Migration(1,2)`、`Migration(2,3)`。
- 所有新字段可空或带默认值；上线前做「旧库升级」回归。

## 7. 结论

- PRD 中 **M1 全部功能技术上可行**，无阻断项；百度地图截图、折线、离线地图能力均已验证存在。
- **M2 的省市识别风险已解除**：后端 `notify.gyzuxing.com` 完全可控，采用 A+B+C+E 组合方案（见 4.2）。
- **M3 的航班航线已收敛**：采用「内置机场库 + 大圆航线参考轨迹」，不使用航旅纵横等私有接口（见 4.3）。
- 建议实施顺序与 PRD 一致：先 M1 打通「记录→合并→分享」，再做 M2 本地互动，最后 M3。

### 已确认
1. 省市识别：采用 **A + B + C + E** 组合，后端负责结构化省市返回与历史回填。
2. 航班航线：采用「内置机场库 + 大圆航线」参考轨迹。
3. 离线范围：M1 仅做「纯轨迹兜底」，离线地图下载放 M3。
